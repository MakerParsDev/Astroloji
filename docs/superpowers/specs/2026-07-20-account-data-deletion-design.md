# Account and Data Deletion Design

## Goal

Provide an authenticated, user-initiated account deletion flow that removes Astroloji application data, Firebase Authentication identity, local Android data, and exposes a public deletion-information page suitable for the Google Play account-deletion URL.

## Scope

- Backend `DELETE /api/v1/users/me` endpoint protected by the existing application JWT middleware.
- D1 deletion for the authenticated user across all user-owned tables.
- KV cleanup for reward and user rate-limit keys.
- Firebase Authentication user deletion through the Identity Toolkit admin REST API using the existing Firebase service account.
- Public `/delete-account` page with Turkish instructions, English summary, support contact, and data-retention disclosure.
- Android Settings destructive action with explicit confirmation, progress, error, success navigation, and local reset.
- Unit, runtime, and Android tests.

## Non-goals

- Cancelling Google Play subscriptions automatically. The page and app will explain that an active subscription must be managed in Google Play and that deleting the account does not itself cancel Play billing.
- Main branch protection.
- Deleting shared horoscope content or application-wide cache objects.

## Backend API

### Endpoint

`DELETE /api/v1/users/me`

Authentication uses the existing app JWT. The JWT provides `user_id` and `firebase_uid`. The endpoint is intentionally bodyless; the Android UI provides a separate destructive confirmation step.

### Success response

HTTP `200`:

```json
{
  "ok": true,
  "user_id": "...",
  "firebase_account_deleted": true
}
```

The endpoint is idempotent for database rows. Repeating it with a still-valid app JWT safely repeats no-op database deletes and retries Firebase deletion. A Firebase `USER_NOT_FOUND` response is treated as already deleted.

### Deletion order

1. Delete D1 rows in one `DB.batch` call:
   - `subscription_events`
   - `user_events`
   - `fcm_tokens`
   - `subscriptions`
   - `users`
2. Delete KV keys with prefixes:
   - `reward:{userId}:`
   - `ratelimit:content:*:{userId}` is short-lived and not efficiently prefix-addressable because the user ID is at the end; it is allowed to expire naturally.
3. Delete the Firebase Auth account by UID.

D1 is deleted first so personal application data is removed even if the external Firebase call has a transient error. The caller keeps its local app JWT on failure and can retry the endpoint. The Android client only clears local state after a fully successful response.

### Firebase deletion

Use:

`POST https://identitytoolkit.googleapis.com/v1/projects/{projectId}/accounts:delete`

with OAuth scope `https://www.googleapis.com/auth/identitytoolkit`, bearer token generated by the existing service-account OAuth helper, and JSON body `{ "localId": firebaseUid }`.

The service account must have `firebaseauth.users.delete`. HTTP success and `USER_NOT_FOUND` are accepted. Other failures return a typed backend error without exposing upstream credentials or response bodies.

### Error behavior

- Missing/invalid app JWT: existing `401` behavior.
- App JWT lacks Firebase UID: `409 FIREBASE_IDENTITY_MISSING`.
- D1/KV failure: `500 ACCOUNT_DELETION_FAILED`.
- Firebase permission/upstream failure after D1 cleanup: `502 FIREBASE_DELETION_FAILED`, safe to retry with the current app JWT.

## Public deletion page

`GET /delete-account` is public and uses the same hardened headers as `/privacy` and `/terms`.

It explains:

- In-app path: Profile/Settings → Account and data → Delete account and data.
- Confirmation and permanent effect.
- Data categories deleted.
- Active Google Play subscriptions are managed separately in Play Store.
- Email fallback: `info@parsfilo.com`.
- Reasonable identity-verification requirements for email requests.
- Shared/anonymized records that are not tied to a user may be retained where legally required or technically necessary.

## Android flow

### Settings UI

Add an “Account and data” card with a destructive outlined button. First tap opens a confirmation dialog. The final confirm dispatches `DeleteAccount`.

UI state additions:

- `isDeletingAccount`
- `showDeleteConfirmation`
- `error`

Effect:

- `AccountDeleted`

On effect, `AstrologyAppRoot` navigates to `OnboardingRoute` and clears the back stack.

### Repository operation

`SessionRepository.deleteAccount()`:

1. Calls backend `DELETE /api/v1/users/me` using the current app JWT.
2. On success:
   - Signs out Firebase Auth locally.
   - Deletes the local FCM token where possible.
   - Clears all Room tables through `AstrologyDatabase.clearAllTables()`.
   - Clears all DataStore preferences, including fallback credentials and onboarding completion.
3. Returns `AppResult.Success(Unit)`.
4. On backend failure, preserves local state and returns a user-facing error so deletion can be retried.

The backend owns Firebase server deletion; Android does not call `FirebaseUser.delete()`, avoiding recent-login requirements and partial client-only deletion.

## Testing

### Backend

- Firebase deletion service requests the correct URL, scope, bearer header, and local ID.
- `USER_NOT_FOUND` is idempotent success.
- Other upstream failures throw a safe typed error.
- Authenticated DELETE batches all D1 statements, deletes reward KV keys, and calls Firebase deletion.
- Missing Firebase UID returns `409`.
- Unauthenticated DELETE returns `401`.
- `/delete-account` returns hardened HTML with instructions, support email, and subscription warning.

### Android

- API method maps to HTTP DELETE.
- Session deletion success calls backend, signs out, clears Room and preferences.
- Session deletion backend failure does not clear local state.
- Settings ViewModel opens/closes confirmation, exposes progress, emits `AccountDeleted` on success, and reports errors.
- Existing lint, unit, debug assemble, and release bundle dry-run remain green.

## Rollout

1. PR and CI.
2. Merge after all checks pass.
3. Run guarded backend production deploy workflow.
4. Verify `/delete-account` returns `200` and unauthenticated DELETE returns `401`.
5. Do not issue a destructive authenticated live request against a real user during smoke testing.
